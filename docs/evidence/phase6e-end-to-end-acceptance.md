**AUTOMATED WORKFLOW ACCEPTANCE USING TEST REVIEW ACTORS**

Phase 6E joins the existing intake, validation, review, approval, publication, typed simulator and debrief in complete offline tests. ## Baseline and scope

The working tree already contained the completed Phase 6A–6D implementation and browser lineage fix. The tests reused actual CLI validation, parser and stores from 6A–6C, including negative integrity and failure-injection cases. Phase 6D already compiled and executed a manually prepared compatible fixture through the real HTTP authorization gate and policy. It also intercepted the actual Timbre request body with an in-process fake transport. Phase 5 tests cover deterministic classifier, policy, timing, consent, cancellation, terminal behavior, pressure, event evidence and privacy. They inject local audio/transport or policy fixtures where the test needs a deterministic boundary. Previous suites exercised intake and publication separately. A single run from each intake through the entire lifecycle, a fake future-generator contract test, and simultaneous submission and checklist writes were the main missing proofs. [Phase 5 acceptance](phase5-final-acceptance.md), [Phase 6D acceptance](phase6d-runtime-isolation.md)

The default mock template intentionally authors distinct ending lines. The new explicit `offline-adaptive-v1` brief profile supplies a candidate compatible with the existing typed-practice contract by using its already authored common safe ending and the medium-intensity authority and fear routes. Its generator provenance is versioned. The original brief, generated records and default generator remain byte-for-byte preserved. Manual import uses an independent test-only adaptation of the checked-in S-92 revision example with S-93 identity, an unverified origin declaration and the same typed-practice contract. S-91 remains the historical two-turn manual-import draft. No runtime, policy, provider, or browser code was changed in Phase 6E.

## End-to-end and negative evidence

- `E2E-MOCK` starts with the repository's benefits brief, invokes the deterministic generator through `LocalDraftStore.generate`, reloads the canonical draft and finishes an isolated typed session in two turns with `SAFE_VERIFIED`.
- `E2E-IMPORT` writes complete fixture JSON to an author-selected file, uses `LocalDraftStore.importFile`, verifies the exact source bytes and canonical content hash, and finishes three typed turns with `MAX_TURNS`.
- `E2E-FAKE-ADAPTER` implements `ScenarioDraftGenerator` in a test, imports its canonical output with an unverified test-only model declaration, and runs the same checks. The declaration raises `ORIGIN_UNVERIFIED` and requires an individual disposition.
- Each checks all 15 variants, 18 examples, educational annotations, ending references, debrief candidates and complete graphs. Each saves and reloads a DRAFT, refuses pre-review and approved-only session creation, refuses incomplete checklists, and requires individual warning dispositions where present. The exact candidate, review snapshot, approval artifact and compiled package hashes are verified. The TEST REVIEWER and TEST PUBLISHER act separately. Approved-only artifacts remain runtime-ineligible.
- Each compiled graph proves 79 prefixes, 66 terminal leaves and maximum depth 3 using the actual policy. The two active continuation lines are `authority.medium` and `fear.medium`. S-91's authoring graph remains 25 prefixes, 21 leaves and depth 2. Graph verification and authored line count are different measurements.
- Each published fixture is visible only in its isolated catalog. The HTTP gate pins publication ID, package hash and policy version, requires consent, refuses real-audio mode, and refuses further turns after the terminal outcome. The trusted approved response is compared with the compiled release text on every turn. One in-memory event and pressure point per committed turn feeds the deterministic debrief. The journal, approval and publication are reloaded from disk. Learner session events are in-memory and have no restart durability contract.
- `SEC-INTAKE` rejects malformed or duplicate-key JSON, oversize input, an unsupported schema version, forged verified model provenance and a mismatched mock profile generator version. The parser and validators also cover empty/invalid UTF-8, unsafe credentials and operational text, extra fields, prototype keys, path or symlink escapes, invalid graph references and lineage. Model origin declarations never create verified provenance.
- `SEC-REVISION` races independent store instances on submit and checklist writes. Each advances the journal exactly once and the losing request returns `REVIEW_CONFLICT`. It rejects stale validator reports, parent reports, reused review IDs and content hashes, and reused parent approval. A new revision requires its own review, checklist, warnings and approval. The original publication remains blocked by `OFFLINE_PROFILE_REQUIRED` after reload. The new approved-only version cannot start a session.
- The focused suite also runs the existing negative gates for rejected/request-changes candidates, forged reviewer or checklist state, stale approval, duplicate or conflicting publication, tampered/missing releases, incompatible graph, unsupported real target, pinned sessions and active safety hold. Existing injected write/link failures prove recovery without phantom publication or audit. The local demo implements publication withdrawal via a safety hold. It has no separate revoke operation.
- Provider checks use a real mocked-text recognizer and fake synthesis results. The published typed-practice path consumes approved response references. Phase 6D sends the actual Timbre adapter payload only to an in-process fake fetch and compares the body text with trusted S-01 content. The tests reject arbitrary caller/TTS text, cross-version references, forged or held release data, stale input and extra audio processing after stop. ## Manual offline guide

1. From the repository root, run `npm run build:packages`. In one PowerShell terminal start the mock-only backend with the following commands. This uses the existing API factory directly and binds only to loopback.

   ```powershell
   @'
   import { createApiServer } from "./apps/api/src/health.ts";
   createApiServer({ environment: "test" }).listen(3186, "127.0.0.1");
   '@ | node --import tsx --input-type=module
   ```

2. In another terminal at the root, set `$env:API_PROXY_TARGET='http://127.0.0.1:3186'` and run `npm run dev --workspace @vaccine/web -- --port 5186 --strictPort`. Open `http://127.0.0.1:5186/#/scenarios`. Verify S-01 is **RUNTIME ELIGIBLE**, S-02/S-03 show **DRAFT**, and S-92 has no playable card.
3. Open **Scenario authoring**. Under **Open a saved draft**, choose **Saved draft JSON** and select `.cache/authoring/mock-80843162b78c5540dc3701cc770c1b2e7bc5544b2fafa1c93979c7bfc8d46235.json` for S-90. Repeat with `.cache/authoring/import-fd46d669704caa567f76cba4d9c6db0dc9728c6a6c88b96d7b121455bae7d3b2.json` for S-91. Verify the respective source and `Errors 0 · Warnings 2` in both previews.
4. For the raw revision check, select `.cache/authoring/import-7d2806433a6b9641c5eaacca23570fa73c8973ca736d90b23d2e88140a360337.json`. Confirm it needs its ancestor. Select `.cache/authoring/mock-c5ab4e92ac5f0062efae8f774c2c4bba02ad86236b5dbaa3586c91efaddca3b5.json` under **Saved ancestor JSON files**. Confirm the revised draft now has zero errors and warnings.
5. Under **Local human review workflow**, choose **Workflow export JSON** and open `.cache/authoring/S-92-v0.1.1-approved.workflow.json`. Expand **Approval and publication record** and **Version and audit history**. Compare the approval, review and publication IDs above with the record and export. Confirm **APPROVED**, submitted validation **current**, `Runtime eligible false`, **PUBLICATION_BLOCKED**, and no remaining `LINEAGE_INVALID`.
6. Verify backend authority against the offline API. The expected response is HTTP 404 with `SCENARIO_NOT_FOUND`.

   ```powershell
   curl.exe -i http://127.0.0.1:3186/api/sessions -H 'Content-Type: application/json' --data-raw '{"scenarioId":"S-92","scenarioVersion":"0.1.1","language":"hi-en","demoMode":false}'
   ```

7. Run `npm run test:phase6e`. For the offline demonstration, follow the `PHASE6E` diagnostics in order. They show generated and imported drafts, validation, TEST REVIEWER and TEST PUBLISHER decisions, trusted response IDs, a bounded session and debrief, and the real catalog refusing unpublished content. Temporary stores close and delete themselves. For interrupted runs, list `vv-phase6e-*` under `[System.IO.Path]::GetTempPath()` and verify any exact path before removing a stale test folder. Preserve the real local registry and authoring cache.
8. Run `npm run check` and `git diff --check`. Review the [machine evidence](phase6e-acceptance.json) and [future adapter plan](../architecture/evon-authoring.md).
